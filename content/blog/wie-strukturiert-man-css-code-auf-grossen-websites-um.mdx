Stellen Sie sich einen Kleiderschrank vor, in den seit zehn Jahren niemand mehr aufgeräumt hat. Jede Saison kam etwas Neues dazu, nichts wurde konsequent aussortiert, und irgendwann findet niemand mehr das passende Hemd, obwohl der Schrank aus allen Nähten platzt. Genau so verhält sich CSS auf gewachsenen Websites. Jeder Entwickler bringt neue Klassen mit. Jede Kampagne, jedes neue Feature legt noch ein paar drauf, und nach zwei oder drei Jahren weiß niemand mehr, welche Regel gerade wofür zuständig ist.

**Große Websites vermeiden CSS-Redundanzen, indem sie Styles in klar getrennte Ebenen aufteilen (CSS Cascade Layers), Komponenten lokal scopen (CSS Modules) statt global zu vererben, gemeinsame Styles konsequent auslagern und ungenutztes CSS regelmäßig mit Tools wie PurgeCSS entfernen.** So wächst das Stylesheet kontrolliert, unabhängig davon, wie viele Personen gleichzeitig daran arbeiten.

Das klingt zunächst nach reiner Entwickler-Hygiene, hat aber einen handfesten wirtschaftlichen Hintergrund. Unstrukturiertes CSS ist unschön, vor allem aber kostet es Ladezeit und Wartungsaufwand. Am Ende zahlt dafür jemand, in barer Münze. Dieser Artikel zeigt, wie das Problem entsteht und mit welchen modernen Werkzeugen es sich in den Griff bekommen lässt, ganz konkret für Betreiber einer größeren Website.

## Wie groß ist das Problem wirklich?

Die Zahlen sprechen eine deutliche Sprache. Laut dem [Web Almanac 2022 des HTTP Archive](https://almanac.httparchive.org/en/2022/css) laden Desktop-Websites am 90. Perzentil rund 256 Kilobyte CSS, im Median liegen etwa 31 Regeln pro Stylesheet vor, und auf mobilen Seiten finden sich am 90. Perzentil teilweise über 2000 Style-Regeln in einer einzigen Datei. Diese Zahlen zeigen etwas Wichtiges: CSS wächst auf großen, ungepflegten Websites praktisch von selbst, wenn niemand aktiv gegensteuert. Es gibt keinen natürlichen Mechanismus, der überflüssige Regeln von allein wieder entfernt.

Riesige Konzern-Websites sind dabei nicht das einzige Beispiel. Auch ein Wiener Online-Shop mit fünf Jahren Geschichte, mehreren Relaunches und wechselnden Agenturen sammelt auf diese Weise CSS-Leichen an, die niemand mehr zu löschen wagt, weil unklar ist, ob irgendwo im Footer oder in einer alten Landingpage noch etwas davon abhängt. Genau diese Unsicherheit ist der eigentliche Kern des Problems. Nicht die Menge an CSS allein macht Ärger, sondern die fehlende Übersicht darüber, was gebraucht wird und was nicht.

## Cascade Layers: Ordnung statt Spezifitäts-Kriege

Ein Grund, warum CSS-Dateien so leicht aus dem Ruder laufen, liegt in der sogenannten Spezifität. Vereinfacht gesagt entscheidet CSS bei widersprüchlichen Regeln danach, welcher Selektor stärker ist, ein ID-Selektor schlägt eine Klasse, eine Klasse schlägt ein Element. Arbeiten mehrere Teams mit unterschiedlichen Konventionen an derselben Website, entstehen daraus schnell kleine Kriege. Team A überschreibt Team B mit einem noch spezifischeren Selektor, Team B kontert mit `!important`, und am Ende hat niemand mehr Freude an der Lösung.

Genau hier setzt eine relativ neue CSS-Funktion an, die sogenannten [Cascade Layers](https://developer.mozilla.org/en-US/docs/Learn_web_development/Core/Styling_basics/Cascade_layers), geschrieben als [`@layer`](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@layer). Damit lassen sich Stylesheets in explizite Prioritätsebenen unterteilen, zum Beispiel `reset`, `base`, `components` und `utilities`. Das Entscheidende: Ist die Reihenfolge dieser Ebenen einmal festgelegt, gewinnt sie unabhängig von der Spezifität der einzelnen Selektoren innerhalb der Ebenen. Eine Regel aus der `utilities`-Ebene schlägt also automatisch eine Regel aus `base`, selbst wenn der Selektor in `base` eigentlich stärker wäre. Damit fällt der Grund für endlose `!important`-Ketten weitgehend weg, weil die Priorität nicht mehr über Selektor-Tricks, sondern über eine bewusst gewählte Reihenfolge gesteuert wird.
